# ESP32 桥代码导读

> 对象：`esp32_ota_bridge.ino`（378 行）
> 目的：让你能一小时内读懂这个文件，而不是被 Arduino 的库吓住。

## 一、先建立"概念映射"（Arduino → 你熟悉的 STM32）

看不懂的最大原因不是逻辑难，而是**名字陌生**。先对照一遍：

| Arduino 写法 | 你熟悉的 STM32 对应物 | 说明 |
|---|---|---|
| `setup()` | `main()` 里的初始化段 | 上电只跑一次 |
| `loop()` | `while(1)` 主循环 | 反复跑 |
| `Serial` | 调试串口（配一个 UART） | ESP32 的 USB 串口 |
| `HardwareSerial McuSerial(2)` | `huart2`（USART2） | 和 STM32 通信的那个串口 |
| `millis()` | `HAL_GetTick()` | 开机毫秒数 |
| `delay(ms)` | `HAL_Delay(ms)` | 阻塞延时 |
| `pinMode / digitalWrite / digitalRead` | `HAL_GPIO_Init / HAL_GPIO_WritePin / HAL_GPIO_ReadPin` | GPIO |
| `String` | 简化版 `std::string` | 能 `+` 拼接、有 `indexOf` |
| `#include <WiFi.h>` | `#include "usart.h"`（但是系统库） | 库随板子包自带 |

## 二、库函数"黑盒清单"（不用查文档，知道这些就够）

### 串口（`McuSerial`，类型 `HardwareSerial`）

| 调用 | 作用 | 对应 STM32 |
|---|---|---|
| `.begin(baud, SERIAL_8N1, rx, tx)` | 初始化串口，指定波特率和引脚 | `MX_USART2_UART_Init()` |
| `.write(b)` / `.write(buf, len)` | 发 1 字节 / 发一段 | `HAL_UART_Transmit()` |
| `.available()` | 现在有多少字节可读（0 表示没数据） | 读 `RXNE` / 看 DMA 计数 |
| `.read()` | 读走 1 字节（没有就返回 -1） | `HAL_UART_Receive()` |
| `.flush()` | 等发送缓冲区真的发完 | 等 `TC` 置位 |

### WiFi / WebServer

| 调用 | 作用 |
|---|---|
| `WiFi.mode(WIFI_AP)` | 设成"热点模式" |
| `WiFi.softAP(ssid, pass)` | 开热点（电脑/手机搜得到） |
| `WiFi.softAPIP()` | 拿到热点自己的 IP（固定 `192.168.4.1`） |
| `WebServer server(80)` | 创建一个 HTTP 服务器，监听 80 端口 |
| `server.on(路径, 方法, 处理函数)` | 注册路由："访问这个路径时调那个函数" |
| `server.begin()` | 开始监听 |
| `server.handleClient()` | **处理一次请求**（必须放在 `loop()` 里反复调） |
| `server.send(状态码, 类型, 内容)` | 回响应（`200` = 成功） |
| `server.send_P(...)` | 同上，但内容在 Flash 里（`PROGMEM`），省 RAM |
| `server.arg("c")` | 取 URL 参数，如 `/cmd?c=4` 里的 `4` |
| `server.upload()` | 取上传文件的分块回调结构 `HTTPUpload` |

### 其它

| 调用 | 作用 |
|---|---|
| `malloc / free` | 申请/释放堆内存（存固件用） |
| `xTaskCreatePinnedToCore(...)` | 创建一个 FreeRTOS 任务（≈ 你平衡车里的任务） |
| `vTaskDelete(nullptr)` | 结束当前任务 |
| `String::indexOf(s)` / `.substring()` / `.length()` | 找子串 / 截取 / 长度 |

## 三、分段导读（按行号）

### 【1–22 行】头注释
不是代码，是"约定说明书"：接线表、协议约定、注意事项。**读代码前先读它**，能省一半力气。

### 【24–46 行】配置 + 全局变量
```cpp
const char *AP_SSID = "OTA-LIAO";   // 热点名
const uint32_t UART_BAUD = 921600;  // 必须和 STM32 的 usart.c 一致
const int PIN_UART_TX = 17;         // ESP32 发 → STM32 PA10
const int PIN_MCU_RST = 4;          // → STM32 NRST
uint8_t *g_buf;  size_t g_len;      // 上传的固件存这里
volatile bool g_busy;  volatile int g_pct;  // 升级状态（给网页查）
```
**要点**：`g_busy` / `g_pct` / `g_msg` 是"后台任务"和"网页"之间的共享状态——这就是为什么网页能显示进度。

### 【48–64 行】两个工具函数
- `appendLog()`：往日志字符串里追加一行，同时打到调试串口
- `crc16_xmodem()`：**和你 STM32 的 `Xmodem_CRC16()` 一模一样**（poly 0x1021，init 0），可以逐行对比两份代码

### 【66–77 行】复位与清缓冲
- `mcuReset()`：拉低 GPIO4 → 等 120ms → 拉高 = **按一下 STM32 的复位键**
- `uartDrain()`：把串口里残留的字节读干净（避免旧数据干扰）

### 【79–115 行】等待工具
- `waitForText("命令行", 160)`：在 160ms 内一直读，直到收到包含"命令行"的文字
- `waitForByte('C', 20000)`：等某一个特定字节，最多等 20 秒

**这两个函数是"聊天式通信"的核心**：不是定时等待，而是"边收边找"。

### 【117–131 行】`enterMenu()`：抢 5 秒窗口
```cpp
mcuReset();                        // 复位板子
for (int i = 0; i < 40; i++) {     // 6 秒内反复试
  McuSerial.write('w');
  if (waitForText("命令行", 160)) return true;
}
```
**为什么 40 次**：STM32 每 1 秒才检查一次首字节，只发一次很可能落在两次检查之间。

### 【133–193 行】`iapDownload()`：核心 60 行
这是整个文件的"主菜"，拆成 5 步看：

| 步骤 | 行号 | 做什么 |
|---|---|---|
| ① 进命令行 | 136 | `enterMenu()` |
| ② 进 IAP 模式 | 138–143 | 发 `'2'`，等"请使用.bin格式文件"，再等 `'C'` |
| ③ 循环发帧 | 145–184 | 每帧 133 字节，等 ACK，失败重传最多 8 次 |
| ④ 拼帧 | 154–161 | `SOH + seq + ~seq + 128B + CRC16(高,低)` |
| ⑤ 收尾 | 186–192 | 发 `EOT(0x04)`，等 ACK，完成 |

**拼帧那 8 行**就是 Xmodem 的全部格式，和你 `boot.c` 里解析的那段一一对应。

### 【195–205 行】`upgradeTask()`：后台任务
为什么要有它？因为升级一次要十几秒，**不能卡住网页请求**。所以：
1. 网页点"升级" → `handleUpgradeStart()` 创建这个任务 → 立刻返回"已开始"
2. 任务在后台跑 `iapDownload()`，边跑边更新 `g_pct`
3. 网页每 400ms 查一次 `/status` 看进度

**这就是"异步"**——你在 STM32 上用 DMA 收发也是同一个思想。

### 【208–287 行】`PAGE`：整个网站
`R"HTML( ... )HTML"` 是 C++ 的**原始字符串**（里面可以随便写引号、反斜杠，不用转义）。

里面三块：
- HTML 骨架（卡片、按钮、日志框）
- `<style>` 外观
- `<script>` 行为：`cmd()`、`upOnly()`、`doUpgrade()`、`poll()`

### 【289–350 行】HTTP 处理函数（6 个）

| 函数 | 路由 | 作用 |
|---|---|---|
| `handleRoot` | `GET /` | 把 `PAGE` 发出去 |
| `handleStatus` | `GET /status` | 返回 JSON：`{busy, pct, msg}` |
| `handleCmd` | `GET /cmd?c=x` | 进命令行 → 发字符 → 读回显 → 返回 |
| `handleUpload` | `POST /upload` | **分块**收文件（开始/中间/结束三态） |
| `handleUploadDone` | `POST /upload` 结束 | 回"收到 N 字节" |
| `handleUpgradeStart` | `POST /upgrade` | 创建升级任务 |

**`handleUpload` 的"分块"**：浏览器不是一次发完 17KB，而是每包 ~1KB 分段发，所以要在 `UPLOAD_FILE_WRITE` 里反复 `memcpy` 拼接。

### 【352–378 行】`setup()` 和 `loop()`
```cpp
setup(): 打开两个串口 → 开热点 → 注册 5 个路由 → server.begin()
loop():  只干一件事：server.handleClient()
```
**注意**：`loop()` 里没有别的东西——因为耗时的活都扔进 `upgradeTask` 了。这是个好习惯。

## 四、三条数据流（串起来看）

### ① 打开网页
```
浏览器 GET /  →  handleRoot()  →  send_P(PAGE)  →  浏览器渲染
```

### ② 点「读版本号」
```
JS: fetch('/cmd?c=4')
 → handleCmd() → enterMenu()（复位+发w）→ 发 '4'
 → STM32 回 "版本号:..."
 → uartReadFor(1500) 收齐 → 原样返回给浏览器
```

### ③ 上传并升级
```
① JS 上传文件 → handleUpload() 分块存进 g_buf
② JS POST /upgrade → handleUpgradeStart() 建任务 → 立即返回
③ upgradeTask 后台跑：
     复位 STM32 → 发 w → 发 '2' → 等 C
     → 133 帧 × 133 字节，逐帧等 ACK
     → 发 EOT → 完成
④ 网页每 400ms 查 /status → 进度条更新
```

## 六、三个关键问题的答案

**Q1：一帧 133 字节，前 3 字节？**
`SOH(0x01)` + `包号 seq` + `包号反码 (0xFF-seq)`，然后是 128 字节数据、2 字节 CRC16（高字节在前）。
反码用来让接收方做一次"包号自校验"：`seq + ~seq == 0xFF`。

**Q2：收到 0x15 为什么能重发？**
`0x15` 只跳出内层 `while`，`acked` 仍是 `false`；外层 `for (retry < 8 && !acked)` 条件成立，于是**同一帧再发**。8 次都失败才报错退出。

**Q3：`enterMenu` 为什么连发 40 次 `w`？**
STM32 每秒只查一次、且只认**首字节**。发一次容易落在两次检查之间，或被残留字节挡住；连发 6 秒覆盖整个窗口。
